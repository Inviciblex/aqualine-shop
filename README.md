# Аквалин — магазин сантехники

[![CI / Deploy](https://github.com/Inviciblex/aqualine-shop/actions/workflows/deploy.yml/badge.svg)](https://github.com/Inviciblex/aqualine-shop/actions/workflows/deploy.yml)
[![Security](https://github.com/Inviciblex/aqualine-shop/actions/workflows/security.yml/badge.svg)](https://github.com/Inviciblex/aqualine-shop/actions/workflows/security.yml)
[![Lighthouse](https://github.com/Inviciblex/aqualine-shop/actions/workflows/lighthouse.yml/badge.svg)](https://github.com/Inviciblex/aqualine-shop/actions/workflows/lighthouse.yml)

Готовый интернет-магазин на React + Vite. Каталог, умный поиск (терпим к
раскладке, транслиту и опечаткам), фильтры (мультивыбор категорий и брендов,
тумблер «только в наличии», цена, сортировка) с сохранением при возврате
из карточки, страница товара с галереей, характеристиками, блоками «С этим
покупают» и похожих товаров,
корзина с подсчётом суммы, оформление заказа с маской телефона, страница «Мои
заказы». Адаптивен под мобильные (на телефоне — умная липкая панель покупки).
Заказы сохраняются в базу, приходят в Telegram, статусами управляет админка.

> 🚀 **Перед публичным запуском** пройдите [`LAUNCH.md`](LAUNCH.md) — единый
> чек-лист: контакты/реквизиты, домен и SEO, карта, `.env` бэкенда, HTTPS,
> бэкапы, реальные фото и smoke-тест.

## 1. Что нужно установить

Только **Node.js версии 18 или новее** (вместе с ним ставится `npm`).
Скачать: https://nodejs.org — берите версию LTS.

Проверьте, что всё установилось, в терминале:

```bash
node -v
npm -v
```

---

## 2. Запуск на своём компьютере (для просмотра и правок)

В папке проекта выполните по очереди:

```bash
npm install        # один раз — скачает зависимости
npm run dev        # запустит сайт для разработки
```

В терминале появится адрес вида `http://localhost:5173` — откройте его в браузере.
Любые изменения в коде сразу видны на странице.

---

## 3. Сборка для сервера

```bash
npm run build
```

Появится папка **`dist/`** — это и есть готовый сайт (обычные HTML, CSS, JS,
без Node.js). Именно её содержимое нужно разместить на сервере.

Проверить собранную версию локально:

```bash
npm run preview
```

## 4. Как развернуть на сервере

> **Авто-деплой (рекомендуется для боевого режима):** настроен CI/CD через
> GitHub Actions + Docker по модели **git flow** — прод обновляется при пуше
> релизного тега `vX.Y.Z` (не при каждом коммите). Pull Request только
> прогоняет тесты и сборку. Ветвление описано в **`GITFLOW.md`**, пошаговый
> деплой — в **`DEPLOY.md`**. Ниже — простые ручные способы для статики.

Сайт статический, поэтому подходит почти любой хостинг. Содержимое папки
`dist/` — это всё, что нужно загрузить.

### Вариант А. Обычный хостинг / VPS (Nginx, Apache, ISPmanager и т.п.)
1. Выполните `npm run build`.
2. Загрузите **содержимое папки `dist/`** (а не саму папку) в корневую
   директорию сайта на хостинге (часто это `public_html`, `www` или `/var/www/html`)
   через FTP/панель управления.
3. Откройте свой домен — магазин работает.

Пример блока для Nginx:

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/aqualine/dist;
    index index.html;
    location / {
        try_files $uri /index.html;
    }
}
```

### Вариант Б. Бесплатные платформы (проще всего)
- **Netlify** или **Vercel**: подключите проект (или перетащите папку `dist/` в
  Netlify Drop), команда сборки `npm run build`, директория публикации `dist`.
- **GitHub Pages**: залейте проект в репозиторий и опубликуйте папку `dist`.
  Важно: если сайт открывается по адресу с подпапкой
  (`username.github.io/repo/`), укажите её в `vite.config.js` →
  `base: '/repo/'`, и пересоберите.

## 5. Как загрузить свои товары

Есть два способа задать товары — выберите удобный.

### Способ А. Google Таблица (удобнее всего, без правки файлов)
Товары редактируются в обычной Google-таблице, сайт читает её при загрузке.

1. Создайте таблицу с такими колонками в первой строке (заголовки — точно так):
   `id`, `sku`, `name`, `category`, `brand`, `price`, `oldPrice`, `description`, `inStock`, `clearance`, `images`, `specs`, `related`.
   Колонка `oldPrice` необязательна — если она больше `price`, на товаре покажется
   старая цена зачёркнутой и бейдж со скидкой. Колонка `clearance` (`да`/`нет`) —
   ставит плашку «Уценка» (для витринных образцов, товаров с мелким дефектом и т.п.).
2. Заполняйте строками по товару. Особые колонки:
   - `brand` — бренд/производитель (необязательно). Если заполнить хотя бы у части
     товаров, в каталоге появится фильтр по бренду, бренд показывается на карточке
     и на странице товара, а также попадает в разметку JSON-LD для поиска;
   - `inStock` — `да` / `нет` (или `true` / `false`);
   - `images` — ссылки на фото через вертикальную черту:
     `https://site.ru/1.jpg | https://site.ru/2.jpg`. Первая ссылка — главное
     фото (превью в каталоге). Оптимальный исходник: 4:3, ~1200×900, WebP/JPEG,
     по HTTPS. Можно не оптимизировать вручную — включите `VITE_IMG_PROXY`
     (см. ниже), и ресайз/кроп/WebP сделает прокси на лету;
   - `specs` — характеристики парами «Название=Значение» через черту:
     `Материал=Латунь | Покрытие=Хром | Гарантия=5 лет`;
   - `related` — `id` сопутствующих товаров через черту (`3|7|10`) для блока
     «С этим покупают». Необязательно: если не заполнить, дополнения подбираются
     автоматически по смежным категориям (к раковине — смесители и т.п.).
3. Файл → «Опубликовать в интернете» → выберите лист и формат **CSV** → опубликуйте.
   Скопируйте полученный адрес (заканчивается на `output=csv` или `format=csv`).
4. В корневом `.env` укажите его:
   ```
   VITE_SHEET_CSV_URL=https://docs.google.com/spreadsheets/d/.../export?format=csv
   ```
   Пересоберите фронт (`npm run build`). Категории и фильтры построятся из таблицы
   автоматически. Меняете товары в таблице — обновляете страницу сайта, и всё
   подтягивается заново (пересборка не нужна).

### Оптимизация фото (image-proxy)

Чтобы не готовить картинки вручную, можно прогонять их через ресайзер на лету —
он приводит любое фото к 1200×900, кропу 4:3 и WebP. В корневом `.env`:

```
VITE_IMG_PROXY=weserv
```

Пусто — фото отдаются как есть. Это build-time переменная: после изменения
нужна пересборка фронта (`npm run build`) или контейнера
(`docker compose up -d --build web`). Работает и с таблицей, и с
`products.json`. Провайдер сейчас один — [images.weserv.nl](https://images.weserv.nl)
(бесплатный сторонний сервис; фото должны быть доступны по публичному HTTPS-URL).

### Способ Б. Файл products.json (по умолчанию)
Если адрес таблицы не задан, товары берутся из **`public/products.json`** — он
лежит рядом с собранным сайтом (после сборки — в `dist/`), поэтому его можно
править прямо на сервере без пересборки. Формат:

```json
{
  "categories": ["Смесители", "Раковины", "..."],
  "products": [
    {
      "id": 1, "sku": "AQ-MX-101", "name": "Смеситель «Поток»",
      "category": "Смесители", "price": 4990,
      "oldPrice": 6490,
      "description": "Краткое описание.",
      "images": [], "inStock": true,
      "specs": [ { "label": "Материал", "value": "Латунь" } ]
    }
  ]
}
```

Запятые между блоками обязательны, после последнего — не нужны (правила JSON).
Поле `oldPrice` необязательно: если оно больше `price`, показывается зачёркнутая
старая цена и бейдж со скидкой. Поле `clearance: true` ставит плашку «Уценка».

По клику на карточку открывается **страница товара** с галереей и характеристиками
(`specs`), адрес вида `#/product/1`. **Фото** (`images`): пустой массив → заглушки;
иначе ссылки или пути к файлам в `public/img/`.

В характеристики стоит добавлять обязательные по закону поля: **страну-изготовителя**
и **гарантийный срок** (пары `Страна=…` и `Гарантия=…` в `specs`). На странице товара
под кнопками покупки показывается блок «оплата при получении / самовывоз / гарантия».

### Информационные страницы (доверие)

Помимо «Контактов» и «Политики конфиденциальности» в подвале есть:

- **«Как выбрать»** (`#/guides`) — гайды по категориям сантехники. Текст правится
  в `src/components/Guides.jsx` (массив `GUIDES`).
- **«Гарантия»** (`#/warranty`) — сроки и порядок обращения, `src/components/Warranty.jsx`.
- **«Возврат и обмен»** (`#/returns`) — условия по ЗоЗПП, `src/components/Returns.jsx`.

> Перед запуском замените в этих файлах плейсхолдеры в квадратных скобках
> (`[claim@example.ru]`, `[ДД.ММ.ГГГГ]`) на реальные контакт для претензий и дату.
> Раскрытые условия возврата — требование закона: без них срок возврата товара
> надлежащего качества расширяется с 7 дней до 3 месяцев.

### SEO

- На главной — разметка `Store` (schema.org) с адресом и часами: правится в
  `index.html`. Перед запуском впишите туда `telephone`/`url` и поменяйте домен
  в `public/sitemap.xml` и `public/robots.txt`.
- На странице товара динамически выставляются `<title>`, `description`, Open Graph
  и JSON-LD `Product` + `Offer` (цена, наличие, бренд) — это `src/seo.js`.
- **Важное ограничение:** сайт использует hash-роутинг (`#/product/1`).
  Поисковики не индексируют адреса с `#` как отдельные страницы, поэтому в выдаче
  товары отдельными карточками **не появятся**, а `sitemap.xml` содержит только
  главную. JSON-LD и мета-теги на странице товара работают для превью при шеринге
  ссылки и для открытой страницы. Чтобы каждый товар индексировался отдельно,
  нужен переход на History-роутинг (настоящие URL `/product/1`); nginx уже отдаёт
  `try_files $uri /index.html`, так что серверная часть к этому готова.

## 6. Заказы: база данных + Telegram (через бэкенд)

Заказы обрабатывает маленький бэкенд (папка `server/`): сайт шлёт заказ на ваш
сервер, тот **сохраняет его в базу данных** (SQLite, файл `orders.db`), присваивает
номер и пересылает в Telegram. Токен бота хранится только на сервере и в браузер
не попадает. По номеру заказа бэкенд отдаёт его статус — это использует страница
«Мои заказы».

**Уведомление отвязано от заказа.** Сначала заказ записывается в базу, и только
потом отправляется в Telegram — поэтому, даже если Telegram в этот момент
недоступен (нет интернета у сервера, блокировка, таймаут), заказ **не теряется**:
он сохранён и виден в админке. Каждый заказ помечается флагом `notified`. Если
уведомление не доставилось, сервер **периодически пробует дослать его сам**
(каждые 5 минут, заказы возрастом от 1 минуты до 3 суток), а в админке у такой
брони показывается отметка «⚠ не уведомлён». При успешной доставке флаг
снимается. Старые заказы (созданные до появления флага) при первом запуске
считаются уже уведомлёнными — задним числом не рассылаются.

### Шаг 1. Бот и чат
1. В Telegram у **@BotFather** создайте бота (`/newbot`) — получите **токен**
   вида `123456789:AAE...`.
2. Узнайте **ID чата**: напишите своему боту любое сообщение, затем напишите
   **@userinfobot** — он покажет числовой ID. Для группы добавьте бота в группу
   и спросите ID у **@getidsbot** (обычно с минусом).

### Шаг 2. Запустить бэкенд
В папке `server/`:
1. Скопируйте `.env.example` → `.env` и заполните:
   ```
   TG_BOT_TOKEN=123456789:AAE...
   TG_CHAT_ID=987654321
   ALLOWED_ORIGIN=https://ваш-сайт.ру     # домен сайта, без слэша в конце
   PORT=8787
   ```
2. Запустите: `node server.js` (нужен **Node.js 22+** — используется встроенная
   база `node:sqlite`, устанавливать и собирать ничего не нужно).
   Проверка: открыв `http://адрес-сервера:8787/api/health`, увидите `{"ok":true}`.

Чтобы бэкенд работал постоянно и сам перезапускался, оформите его как сервис
(пример `systemd` — в `server/README.md`).

### Шаг 3. Указать адрес бэкенда на фронте
1. В корне проекта скопируйте `.env.example` → `.env` и впишите адрес эндпоинта:
   ```
   VITE_ORDER_API_URL=https://ваш-сайт.ру/api/order
   ```
2. Пересоберите фронт: `npm run build`.

Готово: после подтверждения заказа сайт отправит его на бэкенд, а тот — в Telegram.
Если `VITE_ORDER_API_URL` пуст, магазин работает в демо-режиме (заказ выводится в
консоль браузера, клиент видит обычный экран «Заказ оформлен»).

> Где должен жить бэкенд: либо на том же домене за тем же веб-сервером (тогда
> путь `/api/order` проксируется на `localhost:8787` — пример конфига в
> `server/README.md`), либо на отдельном адресе/поддомене (тогда укажите полный
> URL и пропишите ваш домен в `ALLOWED_ORIGIN`). Альтернатива своему серверу —
> бессерверная функция (Vercel/Cloudflare/Netlify Functions): та же логика, токен
> в переменных окружения функции.

## 7. «Мои заказы», статусы и админка

После оформления заказ сохраняется и на устройстве покупателя (в браузере), и в
базе на сервере. Страница **«Мои заказы»** (ссылка в шапке, адрес `#/orders`)
показывает прошлые заказы этого устройства и подтягивает их актуальный статус с
бэкенда. Регистрация не нужна — история привязана к браузеру.

Статусы: `new` (Принят), `confirmed` (Подтверждён), `done` (Выполнен),
`cancelled` (Отменён).

### Админка (управление статусами)
В комплекте есть страница администратора — файл **`admin.html`** (после сборки
лежит рядом с сайтом, открывается по адресу `https://ваш-сайт.ру/admin.html`).
Она показывает все заказы с контактами и составом и позволяет менять статус в один
клик. Есть поиск по номеру/имени/телефону, фильтр по статусу и кнопка «Экспорт CSV»
(выгружает то, что отфильтровано; файл открывается в Excel/Google Таблицах).

Настройка:
1. На сервере в `server/.env` задайте секрет:
   ```
   ADMIN_TOKEN=придумайте_длинную_случайную_строку
   ```
   Перезапустите бэкенд. Если `ADMIN_TOKEN` пуст — админка выключена (эндпоинты
   отвечают «выключено»).
2. Откройте `https://ваш-сайт.ру/admin.html`, в поле «Админ-токен» введите тот же
   секрет, «Адрес API» оставьте `/api` (если бэкенд на том же домене). Токен
   хранится только в текущей вкладке (сбрасывается при закрытии).

Безопасность: открывайте админку **только по HTTPS** (иначе токен можно перехватить),
держите токен в секрете и меняйте при подозрении на утечку. При желании прикройте
`admin.html` дополнительно — базовой HTTP-аутентификацией Nginx или ограничением по
IP. Эндпоинты админки на бэкенде защищены проверкой токена независимо от страницы.

> Альтернатива: статус можно сменить и напрямую в базе SQLite (`server/orders.db`,
> таблица `orders`) любым SQLite-клиентом — админка просто делает это удобно.

### Бэкапы базы заказов

База `orders.db` живёт в Docker-томе. Чтобы не потерять заказы при сбое сервера
или удалении тома, делайте регулярные бэкапы — скрипты уже готовы:

```bash
sh deploy/backup.sh           # создать бэкап в ./backups (сжатый .db.gz)
sh deploy/restore.sh backups/orders-ГГГГММДД-ЧЧММСС.db.gz   # восстановить из бэкапа
```

`backup.sh` снимает **консистентную** копию командой `VACUUM INTO` прямо внутри
api-контейнера (безопасно при работающей базе, в отличие от простого `cp`),
выгружает её на хост, сжимает и удаляет копии старше `KEEP_DAYS` (по умолчанию 30).
По умолчанию используется `docker-compose.prod.yml`; для локального стека —
`COMPOSE_FILE=docker-compose.yml sh deploy/backup.sh`.

Автоматизация по расписанию (crontab, каждый день в 3:30 — копию стоит ещё и
увозить на другой диск/в облако):

```cron
30 3 * * * cd /путь/к/проекту && sh deploy/backup.sh >> backups/backup.log 2>&1
```

`restore.sh` останавливает api, заменяет базу содержимым бэкапа и снова
запускает сервис (спрашивает подтверждение — операция перезаписывает заказы).

## 8. Корзина сохраняется автоматически

Содержимое корзины запоминается в браузере (`localStorage`) и **не пропадает при
перезагрузке** страницы и повторном визите. Логика — в
`src/context/CartContext.jsx`, ключ хранения `aqualine_cart_v1`.

## 9. Тесты и проверки безопасности (CI)

Тесты написаны на встроенном в Node тест-раннере (`node --test`) — **без внешних
зависимостей**, ставить ничего не нужно.

```bash
npm test            # фронтенд: чистая логика utils.js (цена, телефон, скидки)
cd server && npm test   # бэкенд: интеграционные HTTP-тесты API заказов
```

Покрытие тестами (встроенный отчёт Node, без зависимостей):

```bash
npm run test:coverage            # фронтенд (чистые JS-модули)
cd server && npm run test:coverage   # бэкенд
```

Покрываются **чистые модули логики** (`utils.js`, `search.js`, `orders.js`,
парсер каталога, API заказов, сервер). React-компоненты (`.jsx`) тестами не
охвачены — их проверяем вручную и через Lighthouse/линт.

Бэкенд-тесты поднимают настоящий сервер на временной БД и проверяют валидацию,
создание и чтение заказа, защиту админки токеном и ответы 404 — нужен **Node 22.13+**
(встроенный `node:sqlite`).

В CI (GitHub Actions) на каждый Pull Request и релизный тег:
- **`CI / Deploy`** — гоняет оба набора тестов, затем собирает Docker-образы
  (релиз не соберётся, если тесты красные);
- **`Security`** — сканирует репозиторий через **Trivy** (уязвимости в
  зависимостях, секреты, мисконфиги в Dockerfile/compose). Результаты попадают
  во вкладку **Security** репозитория; CRITICAL/HIGH с известным фиксом роняют
  проверку.
- **`Lighthouse`** — аудит собранного сайта (производительность, доступность,
  SEO, best practices). Пороги в `lighthouserc.json`: доступность ниже 0.9 роняет
  проверку, остальные категории — предупреждение (виден регресс, но мёрж не
  блокируется). Полные отчёты доступны как артефакт прогона.

Контейнеры усилены: оба образа работают от непривилегированного пользователя,
с `read_only`-ФС, сброшенными capabilities и `no-new-privileges` (см.
`docker-compose.yml`).

## Структура проекта

```
aqualine-shop/
├─ index.html              # точка входа
├─ vite.config.js          # настройка сборки (base, dev-сервер для телефона)
├─ package.json            # зависимости и команды
├─ .env.example            # шаблон: адрес бэкенда (скопировать в .env)
├─ GITFLOW.md              # модель ветвления (feature/release/hotfix, релизы)
├─ test/                   # юнит-тесты фронтенда (node --test)
├─ .github/workflows/      # CI: deploy.yml (тесты+сборка+деплой), security.yml (Trivy)
├─ public/
│  ├─ products.json        # ← ВАШИ ТОВАРЫ И КАТЕГОРИИ (правится без пересборки)
│  └─ img/                 # сюда кладутся фото товаров
├─ server/                 # бэкенд для заказов (Telegram), запускается отдельно
│  ├─ server.js            # сам сервер-посредник (токен живёт здесь)
│  ├─ test/                # интеграционные HTTP-тесты API (node --test)
│  ├─ .env.example         # токен бота, ID чата, домен (→ .env)
│  └─ README.md            # запуск, systemd, проксирование Nginx
└─ src/
   ├─ main.jsx             # запуск приложения
   ├─ App.jsx              # каркас, навигация, фильтры (+сохранение), маршруты
   ├─ catalog.js           # загрузка товаров: Google Таблица или products.json
   ├─ orders.js            # история заказов покупателя (на устройстве)
   ├─ sendOrder.js         # отправка заказа на бэкенд + проверка статуса
   ├─ index.css            # все стили и адаптив
   ├─ utils.js             # формат цены, маска телефона, иконки категорий
   ├─ context/CartContext.jsx   # корзина + сохранение + тост
   └─ components/          # шапка, фильтры, карточка, страница товара,
                           # корзина, оформление, «Мои заказы», тост
```
